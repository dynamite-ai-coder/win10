Create a complete production-oriented project that attempts to run a full Windows 10 virtual machine inside a Docker-based Render service using QEMU with hardware KVM acceleration when "/dev/kvm" is available.

The goal is to provide a remotely accessible Windows 10 desktop running on Render, with Chrome, ChromeDriver and Selenium available for browser automation. Remote access should be provided through a secure ngrok tunnel rather than exposing Windows RDP directly to the public internet.

IMPORTANT PLATFORM CONSTRAINT:
Do NOT assume that Render provides KVM or nested virtualization.
The application MUST perform a startup capability check for "/dev/kvm".
If "/dev/kvm" is unavailable, clearly report "KVM NOT AVAILABLE" and do NOT silently fall back to slow software emulation unless an explicit environment variable enables the fallback.
The project must be designed so that KVM availability can be tested immediately after deployment.

TARGET RENDER ARCHITECTURE:

Render Service:

- Docker runtime
- Prefer a paid Private Service for the VM/desktop component when possible
- Single service instance only
- Recommended initial compute plan: "8c-32g"
- Recommended VM allocation:
  - 6-8 virtual CPUs
  - 20-24 GB RAM
- Leave enough RAM and CPU for Docker, QEMU, ngrok, monitoring and auxiliary processes
- Persistent Disk: 150 GB SSD initially
- Persistent disk mount path: "/var/lib/windows"
- Do not use multiple instances
- Do not implement horizontal scaling for the Windows VM

The implementation must make CPU/RAM/VM settings configurable through environment variables.

Example environment variables:

VM_MEMORY_MB=24576
VM_CPUS=8
VM_DISK=/var/lib/windows/windows10.qcow2
KVM_REQUIRED=true
ENABLE_TCG_FALLBACK=false

NGROK:

- Use an official/current ngrok method compatible with the current ngrok client.
- The ngrok authentication token MUST be supplied through a Render secret/environment variable.
- Never hard-code the token.
- The tunnel must not expose unnecessary ports.
- Prefer a secure TCP tunnel for Windows RDP if supported by the selected ngrok configuration.
- Also provide an optional HTTP/WebSocket endpoint for a small VM management/status API if useful.
- Never expose unauthenticated management endpoints.
- Document exactly which ports are tunneled.

WINDOWS 10 VM:

- Use QEMU/KVM.
- The project must expect a Windows 10 ISO or Windows installation image supplied by the administrator.
- Do NOT bundle a pirated or redistributed Windows ISO.
- Support a persistent QCOW2 disk image stored under "/var/lib/windows".
- The first boot should allow Windows installation.
- After installation, subsequent container restarts must boot from the persistent QCOW2 image.
- Use UEFI/OVMF where practical.
- Use VirtIO devices where practical.
- Use a suitable virtual disk controller and network device.
- Provide a Windows VM configuration optimized for desktop use.
- Configure QEMU so that KVM acceleration is used whenever "/dev/kvm" exists.
- The VM must use "-enable-kvm" only when KVM is actually available.
- The startup scripts must detect KVM and generate the correct QEMU command automatically.

RDP:

- Windows 10 must have Remote Desktop enabled after installation.
- Provide clear instructions for enabling/configuring Windows RDP.
- Do not expose port 3389 directly to the public internet.
- Use ngrok or another secure tunnel for remote RDP access.
- The project should print the current remote connection information in a safe form without printing secrets.
- Document how to connect using Microsoft Remote Desktop from Windows.
- Document how to connect from Android using an RDP client.

SELENIUM / CHROME:
Inside Windows 10:

- Install Google Chrome.
- Install a compatible ChromeDriver automatically or provide a robust driver-management mechanism.
- Install Python and Selenium.
- Provide a test script that opens Chrome and visits a harmless test URL.
- The test must run with normal GUI/browser rendering, NOT headless mode.
- The system must support normal browser interaction including:
  - clicking buttons
  - filling forms
  - scrolling
  - selecting elements
  - JavaScript execution
  - screenshots
  - downloads
  - uploads where Windows/browser permissions allow it
- The browser should run normally inside the Windows GUI session.

WINDOWS GUI:

- Windows 10 must boot into the normal desktop environment.
- Do NOT replace Windows with Linux desktop software.
- Do NOT use Wine.
- The objective is an actual Windows 10 VM.
- Optimize the VM for interactive desktop responsiveness.

QEMU:
Implement:

- KVM acceleration detection
- CPU topology/configuration
- configurable RAM
- configurable vCPU count
- QCOW2 persistent disk
- UEFI support
- virtual NIC
- VirtIO drivers where supported
- graceful shutdown
- restart handling
- logging
- QEMU PID management
- health checking
- prevention of duplicate QEMU instances

The startup process should roughly work like:

1. Validate environment variables.
2. Check "/dev/kvm".
3. Run a KVM capability test.
4. Validate the persistent disk directory.
5. Create the QCOW2 image if it does not exist and the administrator has explicitly enabled automatic creation.
6. Validate required Windows installation files.
7. Start QEMU.
8. Wait for VM availability.
9. Start required tunnel(s).
10. Start monitoring/health endpoints.
11. Report status.

KVM CHECK:
Create a dedicated script such as:

scripts/check-kvm.sh

It should report:

- whether "/dev/kvm" exists
- permissions
- whether QEMU can access it
- whether KVM acceleration is actually usable
- CPU virtualization information when available
- final result:
  - "KVM AVAILABLE"
  - or "KVM NOT AVAILABLE"

The result must be available both in container logs and through a local health/status endpoint.

CRITICAL FAILURE BEHAVIOR:
If "KVM_REQUIRED=true" and KVM is unavailable:

- Do not boot Windows automatically.
- Exit with a clear error.
- Explain that Render host virtualization access is unavailable.
- Suggest verifying "/dev/kvm" on the selected Render service.
- Do not pretend that the VM is using KVM when it is actually using TCG.

OPTIONAL TCG FALLBACK:
Implement an optional fallback:
ENABLE_TCG_FALLBACK=false

If set to true:

- allow QEMU software emulation
- clearly report "KVM UNAVAILABLE - USING TCG SOFTWARE EMULATION"
- make this status visible in the health endpoint
- never silently enable TCG

PERSISTENT STORAGE:
All Windows VM state must live below:

/var/lib/windows

Store there:

- windows10.qcow2
- UEFI variables
- VM configuration if required
- persistent metadata
- installation state
- optional snapshots/checkpoints

Do not store the main VM disk in the ephemeral Docker filesystem.

Render persistent disk must be mounted at:

/var/lib/windows

Create startup checks that verify the mount exists and is writable before launching QEMU.

Do not store secrets on the persistent disk.
